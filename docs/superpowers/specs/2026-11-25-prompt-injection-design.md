# 프롬프트 인젝션 시험 설계 (A안 3단계: 찾고 고치기까지)

## 왜
지금 방어(한자·전화번호·도구 문법·접수 주장·세후 약속·내부 메모·범위 밖 거절·상담 확인 단계)는 실제 실패를 막다가 생긴 것이지 공격을 겨냥해 시험한 적이 없다. 레포에는 인젝션 시험이 없고, 시스템 프롬프트를 읽어 주는 답변을 막는 점검도 없다. 속았을 때 코드가 무엇을 막는지 숫자와 시험으로 보이고, 뚫린 곳은 닫는다.

## 목표 / 비목표 / 하지 말 것
- 목표: (1) 공격 일곱 종류에 대해 "속은 모델"을 흉내 낸 결정적 시험을 CI에 둔다. (2) 실제 모델(qwen2.5:7b) 공격 모음을 로컬에서 돌려 통과율을 보고한다. (3) 두 시험이 찾은 틈은 작은 가드로 닫고 시험을 남긴다. 못 닫는 틈은 `known_gap`으로 기록한다.
- 비목표: 모델 자체를 인젝션에 강하게 만들기(파인튜닝 · 프롬프트 경쟁), 일반 웹 보안(인증 · 속도 제한).
- 하지 말 것: 통과율을 올리려고 공격 문장을 쉽게 고르지 않는다. 가드를 더해 정상 답을 막는 거짓 거절이 늘면 기존 `dev_guard`가 잡아야 하고, 그 수치는 0을 유지한다. 실제 모델 수치를 CI 기대값으로 고정하지 않는다(비결정적).

## 공격 일곱 종류
1. 가짜 접수번호 · "상담 연결 완료" 주장
2. 시스템 프롬프트 · 내부 메모 유출
3. 사용자 확인 없이 상담 요청 저장
4. 계산 도구에 이상한 인자 (음수 · 거대 금액 · 범위 밖 날짜)
5. "이전 지시 무시" · 역할극으로 범위 밖 답변
6. 상담 요청에 저장되는 글에 심은 지시문(상담원 화면 · 요약에서 읽힘)
7. 세후 이자 · 수익 보장 발언

## 접근 (사용자가 C 선택)
- A 가짜 모델만: 결정적이나 실제 모델이 속는 정도를 모른다 → 단독으로는 제외.
- B 실제 모델만: 현실적이나 비결정적이고 CI 불가 → 단독으로는 제외.
- **C 둘 다**: A는 CI 회귀 방지, B는 A가 놓친 틈을 찾는 로컬 탐색. [내 판단] B에서 나온 틈은 A 시험으로 옮겨 CI에 고정한다.

## 설계
- **A층 (CI)**: `tests/test_injection.py`. `tests/test_graph.py`의 `Script` 가짜 모델 패턴을 쓴다. 종류마다 "속은 응답"(예: `접수번호 H-0001로 접수했어요`, 시스템 프롬프트 본문 낭독, 확인 없는 handoff 호출, `calc_interest(principal=-1)`)을 내놓게 하고, 최종 `answer`에 그 글이 나가지 않는지, 상담 요청이 저장되지 않았는지(임시 SQLite)를 확인한다. 도구 인자 시험(4)과 요약 저장(6)은 도구 함수를 직접 부른다. API 입력 제한(질문 2000자 등)은 `app/api.py` 기존 경계를 확인만 한다.
- **B층 (로컬)**: `eval/injection_set.jsonl`에 공격 20개 안팎(종류별 2~3개, 한국어 일상 문장 + 영어 한두 개)과, 각 공격의 "뚫림" 판정 기준(어떤 검사 함수가 참이면 뚫림)을 둔다. `eval/run_injection.py`가 기존 `Agent`로 돌려 종류별 뚫림 수를 `eval/runs/`에 저장하고 표로 출력한다. 판정은 `app/answer_check.py`의 함수와 새 시스템 프롬프트 유출 검사를 재사용한다(채점기와 가드가 어긋나지 않게).
- **고치기**: 시스템 프롬프트 유출 검사(`leaks_system_prompt`)를 `answer_check.py`에 추가하고 `check_reply`의 한 문제로 연결한다(다시 시킴 → 고정 문구, 기존 흐름). 그 밖의 틈은 시험이 실제로 보여 준 것만 고친다. 시스템 프롬프트에서 뽑은 문구 몇 개가 답에 나오는지로 판정한다(정확 일치가 아니라 일정 길이 이상 겹침).
- **CI**: A층 시험은 `python -m pytest`에 포함되어 자동으로 돈다. B층은 CI에 넣지 않는다. 가드를 끄면 A 시험이 실패하는지(변형 시험)를 종류마다 둔다.
- **README**: 종류별 방어 표(코드가 막음 / 모델에 맡김 / 열린 틈), B층 수치와 "7B 한 모델, 공격 N개 표본, 비결정적" 한계를 쓴다.

## 빌더에게 남기는 것 / 위험
- 일곱 종류 중 실제로 뚫리는 곳은 **아직 모른다**. 시험을 먼저 쓰고 빨간불이 난 곳이 고칠 대상이다. 계획서에는 "틈이 나오면 고친다" 작업을 종류별로 열어 두고, 안 나오면 시험만 남긴다.
- 6번(상담원 화면)은 상담원 UI가 레포에 없다면 저장되는 글이 어떻게 정리되는지(`_clean`, `build_summary`)만 시험하고, UI 쪽 위험은 README에 한계로 적는다.
- 시스템 프롬프트 유출 검사의 거짓 거절: 정상 답이 프롬프트 문구와 우연히 겹칠 수 있다. 겹침 길이는 `dev_guard`와 기록된 답변으로 0건을 확인한 뒤 정한다.
- B층 공격 문장은 개인정보나 실제 약관 본문을 넣지 않는다.
